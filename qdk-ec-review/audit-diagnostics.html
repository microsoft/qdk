Reading the report

A diagnostic starts with its severity and rule. When available, filename:line appears on the next line, followed by the artifact location, discrepancy, and evidence. File lines are one-based, while layer and equation indices are zero-based. (C4 -> stim) names the source and target instruction sets. Reference lists are copyable into qodec checks or readouts; a parity-one relation carries a separate caveat.

  1. 01 Structural1 declaration and reference rules
  2. 02 Semantic10 algebra, action, and parity rules
  3. 03 Informational6 completeness and redundancy rules

print(report) prints errors and warnings, followed by totals. Informational entries remain in report.informational but are not printed individually. INFO examples below use the same block layout to show those fields.

Parity contract: noiseless execution on valid input codewords, with arbitrary incoming Pauli-frame signs. An encoding sign tracks the known Pauli correction associated with that block; it is not a second measurement of the logical state. Readouts must account for these signs. The authored C4 measurement readouts omit them and now receive mismatch diagnostics.

Evidence: readout mismatches show the declared and verified equations, or a short reason no valid equation is available. Check and flag counterexamples show the term values whose XOR produces 1 instead of the required noiseless 0.

Source locations

Diagnostic.source_location is an optional, keyword-only field. It holds a qodec SourceLocation with a filesystem path and one-based line, or None. It does not change severity, diagnostic equality, or grouping by where. The Rule source links below point to the audit implementation; the filename in a message points to the protocol declaration.

Printed locations abbreviate the current user's home directory as ~/. Paths outside that directory, or when the home directory cannot be determined, remain absolute. The stored SourceLocation.path is always absolute. This display form is recognized by VS Code's Windows and Linux notebook path detectors when notebook.output.linkifyFilePaths is enabled; paths containing spaces remain a detector limitation.

Check, flag, and readout mismatches point to the declared equation when it has a location. Other findings use an explicitly identified field when available, then fall back to the containing artifact. A missing equation has no line of its own. Bundle positions refer to the actual outer file, not internal artifact names; externally stored equations refer to their own files.

Locations describe the text read during loading, not later edits to the file on disk. Constructed values, slices, and unlocated fields have no location. Python suppresses locations while the model differs from its loaded snapshot, including edits through shared objects. Saving alone does not update locations; loading the saved file provides a new snapshot. In-memory bundle text has no file of its own, though referenced external files may have locations.

The same information is available through exact model paths. The empty path selects the root; fields use dots, mapping keys use JSON-quoted brackets, and sequence indices are nonnegative. A Node path identifies an occurrence in the current model, not a filesystem location:

node = protocol.resolve('layers[0].gadgets["measure_xx"].readouts[0].equation')
location = node.source_location
if location is not None:
    print(f"{location.path}:{location.line}")

Exact node lookup does not parse circuits or evaluate parity, and has no automatic parent fallback. Invalid syntax raises ValueError; a missing target raises LookupError. The fallback described above belongs to audit. Nodes expose typed accessors; collections use as_sequence() or as_mapping(), not indexing, length, or iteration on the node itself.

Why no incomplete-input-frame rule? Input signs are supplied boundary information; output signs must be determined from input signs and circuit results. A gadget need not remeasure every input sign. An incorrect dependence on an input sign is a check/readout mismatch; an available undeclared measurement relation is a missing check. Pure input-to-output transport is covered by incomplete-output-frame.

Each example is one actual finding with totals omitted. The capture runs enabled one rule at a time. 2 examples retain loaded source locations; edited or constructed scenarios do not. File paths use the report's home-directory abbreviation. A normal audit may report several findings for the same edit; no protocol files were modified to produce these examples.

Invalid model structure
qodec/invalid-structure

Audit finds an invalid protocol declaration: incomplete layers, code-list shapes or capacities, repeated or overlapping boundary supports, action or parameter uses, circuit calls, reference bounds, or artifact connections.

These checks live in audit. qodec load/save enforce only preservation preconditions, so incomplete protocols, unequal code lists, partial readouts, and invalid source text can persist. Findings carry locations; dependent analysis is skipped while unrelated artifacts remain checkable. Opaque circuit-record bounds remain unknown. Whole readout omission is handled by missing-observable and missing-flag errors; a supplied partial list is a structural audit error.

Invalid Clifford map
instruction-set/invalid-clifford

A Clifford action does not preserve commutation relations on the complete generator basis.

Unlisted generators have identity images and participate in the check. The same precondition runs before native Clifford construction, avoiding a native panic for invalid maps. Unsupported generator forms produce a warning. Invalid maps block dependent gadget analyses.

Example · Implicit identity violates commutation

Declare X_0 -> Z_0 without specifying Z_0. Its implicit identity image is also Z_0, so the pair no longer anticommutes.

[ERROR] instruction-set/invalid-clifford
layers[0].instruction_set (C4)
instruction 'invalid_map' action[0]: invalid Clifford map
    Images of X_0 and Z_0 must anticommute: X_0 -> Z, Z_0 -> Z. Unlisted generators have identity images.
ERRORTarget: CodeRule source

Invalid code algebra
code/invalid-algebra

Declared stabilizers or logical operators violate the algebra required of a code.

Stabilizers must commute with each other and all logicals. Each logical X/Z pair must anticommute; distinct logical pairs must commute. The message names conflicting operators. Algebraic code analysis enforces its own preconditions, including consistency of the stabilizer group. qodec can load and save these drafts; audit reports their mathematical errors.

Example · Commuting logical pair

Replace the C4 logical Z operators with its logical X operators. The draft remains representable and serializable.

[ERROR] code/invalid-algebra
codes['C4']
x[0] and z[0] must anticommute
    x[0]: X_0 X_1
    z[0]: X_0 X_1
ERRORTarget: GadgetRule source

Missing observable
gadget/missing-observable

An instruction declares an Observe outcome, but the gadget has no readout binding at that position. One finding is emitted per missing outcome.

A missing observable equation is an error: the gadget does not define how to report a required measurement result. Loading and saving still permit the draft. The check runs after structural and algebraic prerequisites, including when informational findings are excluded. Logical observables precede flags.

    Expected: 2 observable bindings; declared: 0.

Missing flag
gadget/missing-flag

An instruction declares a flag, but the gadget has no binding for it after the Observe outcomes in its readout list.

A missing flag equation is an error: a declared output is undefined. Omission is not an automatic zero; an explicit empty [] equation declares zero and avoids this error. Loading and saving still permit the draft. A supplied partial list remains a structural error. The flag-mismatch rule separately verifies bound equations.

Unsupported action step
gadget/unsupported-action-step

An instruction contains an action step that the logical-action verifier cannot handle. The message identifies the step index and type.

The action verifier accepts Stabilize, Observe, and unconditional Pauli/Clifford steps. An unsupported step skips the action comparison; it does not establish that the instruction is invalid.

Check mismatch
gadget/check-mismatch

A check fires without a fault: its declared equation produces 1 when the required noiseless value is 0.

The message distinguishes a check that always fires from one that can fire in a counterexample. Equation term values show how the XOR was evaluated, including encoding signs and resolved readouts. Repeated terms cancel. Unavailable analysis is a warning. An empty or algebraically empty equation is zero, but supplies no constraint.

Flag mismatch
gadget/flag-mismatch

A bound flag can be one without a fault, violating the noiseless-zero flag contract. The message identifies the flag and its declared equation.

An always-one or sometimes-one noiseless flag is an error. Counterexamples label the equation output and required noiseless value. Contradictory equations are distinguished from definitions that allow either bit value. Unsupported analysis produces a warning; a trivial empty flag is valid.

Action mismatch
gadget/action-mismatch

The circuit action differs from the implemented instruction. One witness identifies a missing or unexpected logical observable/stabilizer, a differing output image, or a sign-parity difference.

A completed comparison emits an error. A handled failure emits a warning, or an informational entry if the failed comparison concerns a preparation with outputs and no inputs. Resetting an input is allowed when it matches the instruction action.

Readout mismatch
gadget/readout-mismatch

A readout does not report the required logical measurement. The message distinguishes an incorrect equation, a result not provided by the circuit, an unexpressible constant inversion, and contradictory or undetermined definitions.

A recoverable mismatch shows only the declared and verified equations. An unavailable result gets a short explanation that circuit bits and incoming signs cannot recover it. Constant inversion is a separate representation limitation, shown as the required expression plus a caveat. Readout messages omit counterexamples. Verification still includes arbitrary incoming frames; unsupported analysis produces a warning.

Incomplete output frame
gadget/incomplete-output-frame

The valid declared relations do not determine an output stabilizer sign from available input signs and circuit measurements.

The test uses the span of the equations, not mere reference presence. Duplicate terms, dependent equations, and invalid checks cannot manufacture a complete frame. Readout definitions do not count as independent known bits. Missing declarations remain warnings. A derived parity-one relation is shown as terms plus a separate caveat; it is not a valid zero-parity check.

Redundant stabilizer
code/redundant-stabilizer

A stabilizer generator is a product of earlier independent generators, or is +I. The message identifies the dependency and the independent rank of the whole declared list.

Only algebraically valid codes receive this informational notice. Inconsistent signs, noncommuting generators, and invalid logical bases remain code/invalid-algebra errors. Redundant generators may be intentional; the rule neither rewrites the code nor changes generator indices. Distinct measurements of related stabilizers may still supply useful fault information. A generator dependency is not evidence that their measurement circuits are redundant.

Vacuous check
gadget/vacuous-check

A declared check is identically zero after expanding selectors and cancelling repeated reference terms, or is explicitly empty.

This is a formal identity for every assignment of the referenced bits and signs, not merely zero on noiseless executions. Such a check cannot detect a fault. Explicit [] remains valid; the notice is informational and is not promoted by promote_warnings=True. An omitted checks list has no entry to report. Vacuous checks are excluded from redundant-check notices. No circuit simulation or readout substitution is used.

Redundant check
gadget/redundant-check

A nonzero formal check equation is the XOR of earlier independent check declarations. The message lists those check positions.

Reference spelling and term order do not affect the test: slices and unions are expanded, and repeated terms cancel. The test treats distinct reference targets as independent symbols, without substituting readout definitions or using noiseless measurement correlations. Repeated measurements at different record positions are therefore not automatically redundant. The rule reports redundant declarations in authored order and does not remove or change them. Redundancy is informational, not a validity or fault-tolerance judgment.

report.ok means there are no errors. To display informational entries:

from pathlib import Path

for diagnostic in report.informational:
    print(f"[{diagnostic.severity.name}] {diagnostic.rule}")
    location = diagnostic.source_location
    if location is not None:
        display_path = str(location.path)
        try:
            relative = location.path.relative_to(Path.home())
            display_path = f"~/{relative.as_posix()}"
        except (ValueError, RuntimeError):
            pass
        print(f"{display_path}:{location.line}")
    print(diagnostic.where)
    print(diagnostic.summary)
    for line in diagnostic.detail.splitlines():
        print(f"    {line}")
    print()

Disable a rule by exact ID, or promote warnings:

report = ec.audit(protocol, disabled=("gadget/missing-realization",))
strict_report = ec.audit(protocol, promote_warnings=True)

Informational entries are not promoted. Structural and algebraic failures block dependent analyses, including shared instruction-set occurrences. A whole-model failure blocks all semantic analysis; unrelated gadgets continue when the failure is local. Code and instruction-set algebra run before gadget verification.

Coverage and provenance

The catalog matches default_rules() exactly: 17 IDs, with 9 ERROR, 2 WARNING, and 6 INFO defaults. The obsolete prepared-input rule and unconditional flag-content-not-checked notice are not registered.

Message examples were captured from fresh loads of the notebook's C4 protocol, with the described in-memory edits, or small circuits over its physical instruction set. Each scenario appears alongside its captured diagnostic text. Apart from omitted totals, error and warning blocks match Report output exactly; INFO entries use the same layout. Line numbers were checked against the loaded files. Source links identify the implementation used for this snapshot.

Analysis limits: the parity verifier currently declines opaque source formats, conditional or selected circuit calls, conditional circuit actions, and circuit flag bits. Logical readout verification declines interleaved logical actions and noncommuting logical measurements. Output logical-frame references after logical measurements or outcome-dependent output frames are reported as unsupported. These cases produce scoped warnings, or informational notices for missing-check discovery, not invented parity results. Empty equations remain identically zero.

A clean report does not prove fault tolerance. qodec preserves resolved declarations; audit checks protocol correctness, including declaration validity and mathematics. Loading a draft is not certification. Missing files, ambiguous definitions, and values that cannot survive a faithful round trip still fail in qodec. Fault-model-dependent checks remain deferred: they need an explicit fault set and a declared detection requirement.
