# Design cases: why each abstraction

[Protocol overview](../../README.md).

This page is for reviewers asking why an abstraction exists. Each was drawn
from concrete cases, the components the QDK runs and the tools it meets, to
find what they share; the table names, for each, a case that needs it and
where it is shown. A case marked planned is not built yet
([Planned features](../planned.md)); the abstraction it needs is.

| Abstraction                                                                     | A case that needs it                                                                                                                                                  | Where it is shown                                                                                                                                                     |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a state per shot (`.shots(OnePerShot)`)                                         | adaptive programs, where each shot takes its own path; a per-shot MPS simulator                                                                                       | [`tests/driver.rs`](../../tests/driver.rs), [`tests/per_shot_executor.rs`](../../tests/per_shot_executor.rs)                                                          |
| `Driver<P>`: a driver that may read a batch's outcomes before it sends the next | runtimes that walk an adaptive program: a QIR runtime for the phase estimation of H₂ (planned); QEP's runtime loop (as `driver_fn`, planned)                          | [`tests/driver.rs`](../../tests/driver.rs); [Planned features](../planned.md)                                                                                         |
| a seed per shot, fixed by the run's seed and the shot's id                      | the same outcomes however the shots are split across runs, on an executor that keeps them apart                                                                       | [Seeds, not generators](../executors.md#seeds-not-generators); [How an executor holds its shots](../executors.md#how-an-executor-holds-its-shots)                     |
| adapters, composed with `>>`                                                    | a noise model, a code's lowering and decoding, a profiler, a debugger, each added without changing the simulator, the program or the other components                 | [`tests/observers.rs`](../../tests/observers.rs), [`tests/static_isa.rs`](../../tests/static_isa.rs)                                                                  |
| `Capabilities` and `Needs`, checked when the chain is built and the job given   | failing before any shot runs: a code over an executor that lacks an instruction of its gadgets; a program that needs what the chain does not offer                    | [What is checked, and when](../composition.md#what-is-checked-and-when)                                                                                               |
| instruction sets described at run time, called by opcode                        | codes loaded at run time, as Qodec gives them                                                                                                                         | [`tests/runtime_isa.rs`](../../tests/runtime_isa.rs); [How applications use it](../instruction-sets.md#how-applications-use-it)                                       |
| `owning_adapter_fn`: a state per shot that owns its way below                   | a runtime that owns its backend for each shot's life, as a Qodec runtime does                                                                                         | [`tests/static_isa/code_runtime.rs`](../../tests/static_isa/code_runtime.rs); [`owning_adapter_fn`](../adapters.md#a-state-that-owns-its-way-below-owning_adapter_fn) |
| shot conditions, carried up with the outcomes                                   | a check a shot fails, such as a post-selection (rejected); a value that could not be determined (unresolved)                                                          | [Shot conditions](../replies.md#shot-conditions)                                                                                                                      |
| `executor_fn` around a backend (a bridge)                                       | the backends and profilers of a tool written before the protocol, such as QEP's                                                                                       | [`tests/existing_tool.rs`](../../tests/existing_tool.rs); [An existing backend and a profiler](../guides.md#an-existing-backend-and-a-profiler)                       |
| `.run_on(placement)`                                                            | an executor that must run on one thread (a device's driver)                                                                                                           | [Where an executor runs](../executors.md#where-an-executor-runs-run_on)                                                                                               |
| an executor written by hand, on `ExecutorLifecycle`                             | a simulator whose shots share one state (an ensemble), in an MPS tensor network prototype                                                                             | [`tests/executor_by_hand.rs`](../../tests/executor_by_hand.rs); [An executor written by hand](../executors.md#an-executor-written-by-hand-executorlifecycle)          |
| `IncrementalReply`: a reply completed later, from elsewhere                     | a debugger that, paused, holds each batch until it is stepped through; an executor on a thread of its own                                                             | [`tests/debugger.rs`](../../tests/debugger.rs); [A debugger: holding and completing work](../guides.md#a-debugger-holding-and-completing-work)                        |
| a refusal's retry class: whether the work may have run                          | a device behind a cloud service, or a simulator on another machine that a runner here drives, reached over a link that may lose, repeat or reorder messages (planned) | [What a rejection says](../rejections.md#what-a-rejection-says); [A lost verdict](../rejections.md#a-lost-verdict-planned-layers-l1-and-l0)                           |
